# v0.21 Windows audio monitoring investigation

The reported symptom is a delay between playing guitar and hearing SimpleDAW's software-monitored input on Windows Audio (Low Latency Mode). Normal playback has sounded fine. Playback starts with media already in the app, while live monitoring adds the input endpoint and the input-to-track processing path.

SimpleDAW's pinned JUCE backend uses WASAPI shared-mode low latency. JUCE queries the driver's allowed shared engine periods through IAudioClient3, selects a supported period, and reads each endpoint's actual stream delay. For duplex audio it uses constraints from both endpoints. The interface and Windows audio driver determine which sample rates and periods are available. A lower device period cannot be forced through this shared-mode backend when the driver does not offer it.

Tracktion's physical wave inputs normally use Auto monitoring, which routes an armed input through the track and the mix graph. When several tracks share an armed input, Auto can route the same instrument through several tracks. Track plugins and latency compensation can add delay. Direct monitoring on the interface is outside SimpleDAW's graph and may be audible alongside the software signal.

Use **Options > Audio Monitoring Report** with the affected track selected. It shows the backend, endpoint names and channel counts, sample rate, processing buffer, driver-reported input and output delays, Tracktion graph delay, armed input routes and monitor mode, and enabled plugins reporting nonzero Tracktion latency. These values describe parts of the signal path and should not be summed as a measured round-trip result.

For a controlled comparison, use the same interface for both endpoints and one armed track. Record the report with a fresh project and no inserted plugins. Compare the smallest stable driver-supported buffer with the original setting. Then repeat with the original track or project. Check the interface's direct-monitor setting when comparing the audible delay. An external loopback measurement or the interface test is needed to establish the actual capture-to-output delay and isolate the source.

The correction leaves the audio engine, buffer negotiation, compensation and monitor defaults unchanged. The hosted CI runner tests input routing and recording setup without the affected interface. The cause and magnitude of the reported delay await the Windows hardware check.
